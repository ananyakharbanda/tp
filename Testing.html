Testing guide

Running tests

You can run tests in two ways.

  • Method 1: Using IntelliJ JUnit test runner
    • To run all tests, right-click on the src/test/java folder and choose Run 'All Tests'
    • To run a subset of tests, you can right-click on a test package, test class, or a test and choose Run 'ABC'
  • Method 2: Using Gradle
    • Open a console and run the command gradlew clean test in Windows Command Prompt, or ./gradlew clean test in PowerShell, Mac, or Linux.

Link: Read this Gradle Tutorial from the se-edu/guides to learn more about using Gradle.

Types of tests

This project has three types of tests:

  1. Unit tests target the lowest-level methods and classes.
    For example: seedu.address.commons.util.StringUtilTest
  2. Integration tests check how multiple code units work together; the individual units are assumed to work.
    For example: seedu.address.storage.StorageManagerTest
  3. Hybrid tests combine unit and integration testing. These tests check both the individual units and how they work together.
    For example: seedu.address.logic.LogicManagerTest

Manual testing

The Developer Guide's manual testing appendix contains the test-data setup, command scenarios, expected results, persistence and failure checks, and performance verification procedure. Use the display scenarios below alongside that appendix for release testing.

Display settings and window usability

WindowPlacementTest checks startup sizing against usable screen bounds, including a 1280 × 720 display at 150% scaling with 60 physical pixels reserved for a taskbar (about 853 × 440 logical pixels). It also checks restored preferences from larger or disconnected displays, secondary monitors, and minimum sizing. These geometry tests run without a graphical desktop; they do not change the operating system's display settings.

For release testing, use the following native display settings and leave the taskbar or dock visible:

Display resolution Scaling Approximate logical desktop size before taskbar/dock
1280 × 720 100% 1280 × 720
1280 × 720 150% 853 × 480
1920 × 1080 100% 1920 × 1080
1920 × 1080 150% 1280 × 720

For each setting:

  1. Launch the application with fresh preferences. Check that the entire window, including its title bar and bottom status bar, fits inside the usable desktop.
  2. Add enough students to require scrolling. Confirm that the command box, command feedback, menu bar, and bottom status bar stay visible while the student list scrolls to the last student.
  3. Run add n/Display Check i/Z9999999Z e/display@example.com, find n/Display, and list. Check that typing and pressing Enter work, feedback is readable, and the list updates.
  4. Open Help using help and F1 while the command box is focused. Check that the message and Copy URL button fit on screen, and that copying the URL works.
  5. Resize to the minimum 450 × 400 window. Confirm that the command box and feedback remain visible and at least one ordinary student card fits in the scrollable list. Resize larger and repeat the commands.
  6. Save a larger window on a larger display, exit, switch to 1280 × 720 at 150%, and relaunch. Confirm that both the restored size and position fit the usable desktop. Repeat after disconnecting a secondary monitor.

A rendered layout at the equivalent logical viewport is useful during development. Native release testing is still needed to check each operating system's window borders, taskbar, font rendering, and scaling behaviour.

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

UI component

The API of this component is specified in Ui.java

The partial class diagram shows UI ownership and object creation. Common UiPart inheritance and dependencies outside the UI package are omitted from the drawing and described below.

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, AttendanceListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects and AttendanceReport objects from the model.
  • shows an AttendanceListPanel in place of the PersonListPanel while a command result carries an attendance report. See Viewing attendance.

Logic component

API : Logic.java

Here's a (partial) class diagram of the Logic component:

The add and delete diagrams show command execution on a pending model. The separate save-before-publish diagram shows how LogicManager saves and publishes those changes.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. A read-only command queries or filters the live model. A modifying command runs on a pending model; LogicManager saves the pending records before publishing them. Undo uses its separate restoration path.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

The parsing class diagram uses the implemented AddCommandParser as a representative. Other command parsers use the same Parser interface; their individual dependencies are omitted.

How the parsing works:

  • When called upon to parse a user command, the AddressBookParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The AddressBookParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

Model component

API : Model.java

The first class diagram shows model ownership and interfaces. Student fields are expanded in the second; attendance-report classes are shown under Reporting attendance.

The Model component,

  • stores the student data i.e., all Person objects (which are contained in a UniquePersonList object).
  • uses studentId as the domain identifier for Person duplicate checks. The JavaFX id label in PersonListCard.fxml is only the displayed list index, not the student's identifier.
  • stores group labels as Label objects inside each Person.
  • stores attendance as AttendanceRecord objects (a date and a group) inside each Person, and builds AttendanceReport objects from the student list on request. Each report contains AttendanceEntry values pairing a student with their presence status. Reports are derived by the logic layer using AttendanceReport#of; they are not saved in the address book.
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user's preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Alternative (not implemented): The design below keeps a unique list of labels in AddressBook, and each Person references values from that list. This lets AddressBook maintain one value object per unique label instead of each Person holding its own objects.

Storage component

API : Storage.java

The Storage component,

  • can save both student data and user preference data in JSON format, and read them back into corresponding objects.
  • expects each stored Person JSON object to contain a valid studentId. There is currently no migration or default-value strategy for old data files missing this field.
  • stores group labels through JsonAdaptedLabel. Missing or null labels fields are treated as empty label sets for compatibility with older data files.
  • ignores legacy tags fields when loading older data files and omits them when saving.
  • reports loading failures as DataLoadingException, distinguishing unreadable files, invalid data, and duplicate Student IDs. See Loading student data at startup.
  • writes student data atomically and reports a data folder that cannot be created as DataStorageLocationException. See Saving before publishing changes.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Implementation

This section describes some noteworthy details on how certain features are implemented.

Group labels

An optional group label is assigned when creating a student with add ... l/LABEL_NAME. Label validates the value, and ParserUtil#parseLabel trims command input before constructing it. JsonAdaptedLabel and JsonAdaptedPerson persist labels under each student's labels JSON field. EditCommand preserves labels unless label changes are requested, and PersonCard renders them in its FlowPane. Existing saved labels remain compatible, including records containing multiple labels.

Edit command

Format: edit i/STUDENT_ID [n/NAME] [e/EMAIL] [r/REMARK] [l/LABEL_NAME]... [dl/LABEL_NAME]...

EditCommandParser checks command structure and parses the Student ID and requested field changes. It collects repeated l/ and dl/ values into the EditPersonDescriptor. An empty l/ requests clearing all labels and is rejected if combined with another label change. An empty r/ becomes an empty remark.

EditCommand finds the student by Student ID in the complete student list, so a filtered view does not change the target. It builds a replacement Person, keeping fields that were not supplied. For labels, it copies the student's set, removes each dl/ label, then adds each l/ label. Matching is case-insensitive. Removing a missing label or adding one already present throws a CommandException, leaving the record unchanged. An empty l/ produces an empty label set. The command then replaces the student through Model#setPerson; LogicManager saves the pending model before publishing it to the live model.

Mark and unmark attendance

Command formats:

mark i/STUDENT_ID d/YYYY-MM-DD l/GROUP
unmark i/STUDENT_ID d/YYYY-MM-DD l/GROUP

The accepted inputs, examples, and feedback are documented under Recording attendance and Removing attendance in the User Guide.

Parsing and validation

AddressBookParser routes each command to MarkCommandParser or UnmarkCommandParser. Both tokenise i/, d/, and l/, accepting any parameter order and exactly one non-empty value for each. Their structure checks follow the same order: internal line breaks, unknown prefixes, preamble text, repeated prefixes, then missing or empty values. Repeated and missing/empty checks use i/, d/, l/ order. The general command parser rejects multiline input before command-specific parsing.

Both parsers reuse ParserUtil#parseStudentId, ParserUtil#parseDate, and ParserUtil#parseLabel, in that order. The date parser requires a valid calendar date in the strict YYYY-MM-DD format. The parsers then construct MarkCommand or UnmarkCommand with the validated values.

Matching and updating records

Both commands search Model#getAddressBook().getPersonList() by normalised Student ID, so a student hidden by the active filter can still be updated. A missing student throws CommandException before any change.

  • MarkCommand first finds a current group label using case-insensitive matching. It creates an AttendanceRecord(date, matchedGroup) and rejects an existing entry for that date and group. Otherwise, it adds the record to a copy of the student's attendance set.
  • UnmarkCommand searches the existing attendance set using AttendanceRecord#equals, which compares dates exactly and group names case-insensitively using Locale.ROOT. A missing record throws CommandException. Otherwise, it removes the matched record from a copy of the set. Current group membership is not required: EditCommand retains attendance when labels change, and historical records must remain removable. Success feedback uses the matched record's stored group spelling.

Each command constructs a replacement Person, retaining every other field, and calls Model#setPerson. Other attendance entries and the active filter remain unchanged. unmark removes the specified attendance entry; like other successful data changes, it can later be reversed by undo.

Saving and sequence diagrams

Both commands return true from Command#isModifyingData. LogicManager blocks them after a startup loading failure, executes them on a pending model, saves that model, and only then publishes it to the live model. Parsing, command, or save failures preserve the live records, filter, and previous saved file. The existing attendance JSON representation is reused; no storage format change is needed.

The following object sequences focus on command execution after parsing and the startup-data check. Each assumes an existing student and valid attendance state for that operation. They stop when the pending model has been updated; the shared save-before-publish flow runs next.

Adding student information

Command format: add n/NAME i/STUDENT_ID e/EMAIL [r/REMARK] [l/LABEL_NAME]. One optional group label can be assigned during add; Label defines its validation rules. Accepted values are documented in the UG field rules; exact messages and validation order are in Appendix: Errors.

Validation and identity

  • ArgumentTokenizer recognises supported prefixes at the start of arguments or after whitespace, including tabs.
  • AddCommandParser checks line breaks, unknown alphabetic prefixes, preamble text, repeated prefixes, missing mandatory fields, then empty mandatory fields. Errors are reported before parsing field values. Repeated/missing/empty checks follow n/, i/, e/ order; repeated r/ and l/ are checked after them.
  • ParserUtil trims values and converts invalid fields into ParseExceptions. Model constructors also validate, so records created by storage or other callers follow the same rules.
  • Name accepts 1–100 Unicode code points after trimming and collapsing repeated spaces, requires a letter, and permits Unicode letters/combining marks, spaces, apostrophes, hyphens, and periods. Case is preserved.
  • StudentId accepts nine ASCII alphanumeric characters and stores uppercase using Locale.ROOT. Person#isSamePerson compares this normalised ID, not the name or email.
  • Email enforces the supported ASCII format, local-part limit of 64, overall limit of 254, domain-label limits of 63, and a final label of 2–63 letters. Only the domain is lowercased using Locale.ROOT.
  • Remark accepts at most 4,000 Unicode code points; command parsing trims only surrounding whitespace. Empty or omitted remarks become empty strings. r/ can appear anywhere and does not consume later parameters.
  • Label accepts 1–60 Unicode code points and requires at least one letter or digit. It permits letters, combining marks, digits, spaces, hyphens, underscores, apostrophes, parentheses, and periods. Empty labels are rejected, omitted labels become an empty label set, and l/ can appear anywhere without consuming later parameters.

For example, add n/ Alex Tan i/a0123456b e/Alex@EXAMPLE.COM l/Tutorial 1 r/Quiz: 8/10 creates a student with name Alex Tan, ID A0123456B, email Alex@example.com, label Tutorial 1, and remark Quiz: 8/10. An alphabetic token such as x/value is rejected even inside a remark; 8/10 and URLs remain literal text. A duplicate ID rejects the complete command without merging any details or remarks.

Saving before publishing changes

LogicManager coordinates this transaction for add, edit, delete, mark, unmark, and clear. undo uses the separate restoration flow described in Undoing data changes.

  1. Parse the input into a Command, then check startup data availability. Command#isModifyingData identifies data-changing commands; future modifying commands must override it too.
  2. Copy the live address book for undo, and create a pending ModelManager with the current records, preferences, and filter. Execute the command on this pending model. A command error stops the transaction before saving.
  3. Pass the pending address book to Storage#saveAddressBook. The storage implementation locks the data file's sidecar, checks for external changes, and atomically replaces the file as described below.
  4. After a successful save, retain the previous address book for undo if the records changed, then publish the pending records and filter. Only then return success and refresh or close an open attendance report. A save failure leaves the live records, view, and undo history unchanged. The attempted save does not replace the destination file, including newer contents written by another window.

Storage conflict detection and replacement

JsonAddressBookStorage normalises the absolute target path and serialises in-process file access with FILE_ACCESS_LOCK. During each save it creates the parent folder, opens the sibling addressbook.json.lock, and calls FileChannel#tryLock. An unavailable lock gives DataFileInUseException. The lock is released after saving, but the sidecar file remains so concurrent writers continue locking the same file identity.

While holding the lock, storage writes a complete temporary JSON file beside the destination and reads its bytes. It compares the destination's current bytes with the bytes remembered from its last successful read or save. A difference, including a file created or removed by another writer, gives DataFileChangedException. Otherwise, Files.move with ATOMIC_MOVE and REPLACE_EXISTING replaces the destination and the new bytes are remembered. There is no fallback overwrite when atomic replacement is unsupported. Temporary-file cleanup is attempted after success or failure; a cleanup failure is logged.

The lock coordinates TeachAssist writers. External editors do not participate in that lock, so users should still close TeachAssist before editing its data file. This protection applies to student data, not preferences.json.

LogicManager#saveStudentData maps these exceptions to the distinct messages and recovery actions in Saving errors. A changed file requires restarting to load current data; a busy writer can be retried. JsonAddressBookStorageConcurrencyTest covers stale writers and lock contention.

The add sequence below shows only AddCommand#execute on the pending model, for a student with a unique ID. Field parsing and the shared save transaction are outside its scope.

If startup loading fails, MainApp keeps the original file and starts with an empty fallback model. LogicManager blocks modifying commands, list, find, and attendance until the file is fixed and the application is restarted. See Blocking student-data commands after a failed load.

Successful adds display Added student ID: NAME., followed by Remark: TEXT when the remark is non-empty, and the total student count on the next line. The count uses the complete record list. PersonCard displays labels and non-empty remarks with wrapping, and hides the remark field for empty remarks. JSON storage preserves remarks and defaults missing/null remark fields to empty strings.

Find command

Command format: find n/KEYWORD [MORE_KEYWORDS]..., find i/KEYWORD [MORE_KEYWORDS]..., find e/KEYWORD [MORE_KEYWORDS]..., find r/KEYWORD [MORE_KEYWORDS]..., or find l/LABEL_NAME. Supply exactly one search field. Label searches replace the former standalone filter command. See the User Guide for examples and Find errors for error messages and validation order.

Validation and matching

  • ArgumentTokenizer recognises n/, i/, e/, r/, and l/.
  • FindCommandParser checks words before the first prefix, unknown prefixes, repeated prefixes, missing prefixes, multiple search-field types, empty values, and then label validity, in that order.
  • Name, ID, email, and remark values are split into whitespace-separated keywords. NameContainsKeywordsPredicate, StudentIdContainsKeywordsPredicate, EmailContainsKeywordsPredicate, and RemarkContainsKeywordsPredicate match any keyword using StringUtil#containsIgnoreCase, including partial matches.
  • RemarkContainsKeywordsPredicate searches Person#getRemark().value only. Empty remarks do not match non-empty keywords. Numeric slash text such as 8/10 is accepted under the existing prefix rules.
  • A label value is kept whole, validated by ParserUtil#parseLabel, and passed to LabelMatchesPredicate. This predicate lowercases both the requested and stored label names with Locale.ROOT, then compares the complete values, using the same rule as EditCommand and JsonAdaptedPerson. Internal spaces are preserved. This also handles Unicode lowercase expansions, such as İ becoming i followed by a combining dot, while keeping I and the dotless ı distinct.

For example, find n/alex david finds names containing either keyword, while find l/Discrete Math Tutorial finds students with that complete group label. find l/Tutorial does not match Discrete Math Tutorial. find r/recursion loops searches remarks for either keyword, and find r/curs also matches recursion. Empty r/, repeated r/, and combinations such as find r/recursion l/Tutorial 1 are rejected before execution.

Execution, persistence, and startup behaviour

AddressBookParser → FindCommandParser → FindCommand
FindCommand → Model#updateFilteredPersonList

Every search replaces the active predicate and evaluates the complete student list; searches do not narrow the previous result set. FindCommand returns the standard N students listed. (or 1 student listed. for one match) feedback. Zero matches clear the view. list restores all students. Invalid commands preserve the previous view.

FindCommand remains read-only and executes without saving when student data is available. After a startup loading failure, LogicManager blocks it until the data file is fixed and the app restarted. A missing data file or a successfully loaded empty file permits a search with zero results. Student records and the saved file are unchanged by a search.

Deleting student information

Command format: delete i/STUDENT_ID. The display index is not used to identify students for deletion.

DeleteCommandParser accepts exactly one non-empty i/. It rejects line breaks, unknown prefixes, preamble text, repeated IDs, missing IDs, and empty IDs before calling ParserUtil#parseStudentId. ArgumentTokenizer#findUnknownPrefix shares the same case-sensitive alphabetic-prefix detection with add. An invalid Student ID retains the field constraint message instead of being replaced with a usage error.

DeleteCommand stores the validated StudentId and searches model.getAddressBook().getPersonList() for an exact normalised ID match. It retrieves the existing Person and passes that object to model.deletePerson. This removes the entire record, including remarks and labels, without separately deleting its fields. The complete record list is searched so a student hidden by a filter can still be deleted.

For example, after find n/Benson, delete i/a1234567b removes Alice's A1234567B record while the displayed Benson results remain unchanged. If Alice is already absent, the command reports Student with ID A1234567B is not in the records. and changes no data. Successful feedback is Deleted student A1234567B: Alice Pauline.

Deletion preserves the current filter and returns true from Command#isModifyingData. LogicManager therefore performs it on the temporary model, saves the proposed records, and only then publishes the change. If saving fails, the live record, filter, and previous saved file remain unchanged. If startup loading failed, deletion is blocked by the existing loading guard.

Viewing attendance

The command attendance d/YYYY-MM-DD l/GROUP shows which current members of a tutorial group were marked present on a date. Its accepted values and messages are documented in the User Guide. Recording and removing attendance are described in Mark and unmark attendance.

Storing attendance

Each Person holds an immutable set of AttendanceRecord objects. A record is a date and a group Label. Two records are equal when their dates match and their group names match after toLowerCase(Locale.ROOT), the same rule used to reject duplicate labels. This makes the date and group pair unique for each student.

JsonAdaptedPerson saves the records under each person's attendance field, and JsonAdaptedAttendanceRecord validates each date and group when loading. A missing or null attendance field loads as an empty set, so data files written before attendance existed still load. Records are stored inside the Person, so deleting a student deletes their records, and edit keeps them.

Only presence is stored. A student is absent when they have no record for the date and group.

AttendanceCommandParser checks d/ and l/ in the same order as the mark and unmark parsers, then reuses ParserUtil#parseDate and ParserUtil#parseLabel.

Reporting attendance

AttendanceReport#of(students, date, group) keeps the students whose current labels include the group, in the order given, and pairs each one with whether they have the matching record. It also gives the present and absent totals. Membership comes from current labels, so a student who lost the label is left out even if their records remain.

AttendanceCommand is read-only. It builds a report from model.getAddressBook().getPersonList(), not the filtered list, so find does not hide group members. It returns CommandResult#showingAttendance(message, report).

Showing and refreshing the attendance view

CommandResult carries an optional AttendanceReport. MainWindow#executeCommand shows an AttendanceListPanel in the student list area when a result carries a report, and shows the PersonListPanel again when it does not. Each AttendanceCard shows a member's name, Student ID, and a Present or Absent badge.

LogicManager remembers the report being displayed in displayedAttendance. After each successful command it:

  • stores the result's report if there is one;
  • otherwise, if the result reports an attendance update and a report is displayed, rebuilds that report from the live model and attaches it to the result with CommandResult#withAttendanceReport. MarkCommand and UnmarkCommand report updates by returning CommandResult#updatingAttendance(message);
  • otherwise, clears displayedAttendance, so the UI returns to the student list.

Because the rebuild happens after saving and publishing, the view only changes once the change is saved. A failed command throws before this step, so the view stays as it was. A successful undo returns a plain result, so it closes the view; the restored records are shown in the student list.

Design considerations

Aspect: Where to keep the displayed report

  • Alternative 1 (current choice): LogicManager remembers it and attaches a refreshed report to the result.
    • Pros: MainWindow stays a simple renderer, and the refresh rules are tested without JavaFX.
    • Cons: LogicManager holds a small piece of display state.
  • Alternative 2: MainWindow remembers the open date and group and asks Logic for a new report after mark.
    • Pros: Display state stays in the UI.
    • Cons: The UI must know which commands change attendance, and the refresh can only be tested through the GUI.

Aspect: How to record absence

  • Alternative 1 (current choice): Store only presence; absent means not marked.
    • Pros: One command per present student, and no need to finalise a session.
    • Cons: An absence cannot be distinguished from a session the TA has not taken yet.
  • Alternative 2: Store explicit Present and Absent records.
    • Pros: Every student has a recorded status for every session.
    • Cons: Needs a way to record or finalise absences, and more data to keep consistent when labels change.

Loading student data at startup

Commands available after a failed load are documented in the User Guide. Exact startup messages and data-file rules are in Loading errors.

Loading and error reporting

The loading path is:

MainApp#initModelManager → StorageManager → JsonAddressBookStorage → JsonSerializableAddressBook
MainApp#initLogic → LogicManager
  1. JsonAddressBookStorage#readAddressBook returns Optional.empty() if the data file does not exist.
  2. For an existing file, JsonAddressBookStorage reads its bytes once with Files.readAllBytes, decodes them as UTF-8, and parses them with JsonUtil#fromJsonString. Failure to read the bytes gives Unable to load student data.; invalid JSON gives Unable to load student data. The data file may be corrupted or invalid. Both are reported as DataLoadingException.
  3. JsonSerializableAddressBook#toModelType converts records in file order. A missing or invalid field throws IllegalValueException, which is reported with the corrupted or invalid message. A repeated Student ID throws DuplicateStudentIdException, a subclass of IllegalValueException. JsonAddressBookStorage catches it first so that its specific message, Unable to load student data: duplicate Student ID A0123456B detected., is kept. Student IDs are compared after normalisation to uppercase. Only after conversion succeeds does storage remember the same bytes for conflict detection on future saves. A missing file is remembered as absent.
  4. MainApp records the outcome as the startup message: N students loaded. (1 student loaded. for one record), the no-existing-data message, or the DataLoadingException message.
  5. MainWindow#fillInnerParts shows Logic#getStartupMessage in the result display when the window opens.

Blocking student-data commands after a failed load

When loading fails, MainApp starts with an empty AddressBook and passes isStudentDataAvailable = false to LogicManager. LogicManager#execute parses each command first, so malformed commands still receive their usual error messages. It then rejects modifying commands (including undo), list, find, and attendance with Student data is unavailable because loading failed. Fix the data file and restart.

This prevents the empty in-memory list from being saved over the user's data file, which may still be recoverable. list, find, and attendance are blocked because the empty fallback model is not a successfully loaded dataset. help and exit remain available. A missing file or a successfully loaded empty file still permits student-data commands and genuine zero-total attendance reports. After fixing the file, restart to retry loading.

Saving is described in Saving before publishing changes.

Design considerations

Aspect: What to do when the data file cannot be loaded

  • Alternative 1 (current choice): Start with an empty list, keep the file, and block commands that change or query student data.
    • Pros: The user's data file is never overwritten, and the user sees why loading failed.
    • Cons: The app cannot be used to change records until the file is fixed.
  • Alternative 2: Start with an empty list and allow modifying commands, as in AddressBook-Level3.
    • Pros: The app remains fully usable.
    • Cons: The first save overwrites the original file, losing data that might have been fixable.

Undoing data changes

LogicManager owns an in-memory deque of complete AddressBook snapshots. It retains at most 100 prior states. The snapshots contain student data only; GUI settings and the current find predicate are not recorded. History begins empty on every application start and is never written to JSON.

Before a normal data-changing command runs, LogicManager copies the live address book. It executes the command on the existing pending model and saves that proposed address book. Only after the save succeeds does it append the pre-change snapshot, discarding the oldest snapshot first when the deque is full, and publish the pending model. If the saved address book equals the snapshot, as for clear on an empty list, no snapshot is appended, so undo never reports a change it cannot show. Thus parsing, validation, execution, or save failures leave the live records and undo history unchanged.

For undo, LogicManager examines the newest snapshot without removing it. It saves that snapshot before replacing the live address book, resets the displayed list with Model.PREDICATE_SHOW_ALL_PERSONS, and then removes the snapshot. Showing all students makes the restored records visible; filters are not part of undo history. If saving fails, live records, the displayed list, the saved file, and history remain unchanged. If no snapshot exists, it returns Nothing to undo. without saving and preserves the student filter. Both successful outcomes close an open attendance report.

Undo is destructive: restoring a snapshot discards the state being reversed, so there is no redo or forward branch. A later successful data change records the then-current state as a new predecessor.

Design consideration

Aspect: How undo stores prior state:

  • Current choice: Complete address-book snapshots in LogicManager.
    • Pros: One transaction handles every data-changing command and keeps saving before publishing explicit.
    • Cons: Each retained state copies the address-book list structure.
  • Alternative: Command-specific inverse operations.
    • Pros: Can retain less state for some commands.
    • Cons: Every data-changing command must implement and validate its own reverse operation.

Loading errors

Condition Message Recovery
File cannot be read, e.g., permission denied Unable to load student data. Close the app, restore read access or a readable backup, and restart.
Malformed JSON, extra root values/trailing garbage, null root, wrong structure, or invalid record Unable to load student data. The data file may be corrupted or invalid. Close the app, fix or restore the file, and restart.

The entire JSON document is deserialized before model validation. JsonUtil#fromJsonString uses a Jackson 2.7 parser and explicitly checks nextToken() after binding the root value; additional tokens or invalid trailing content fail loading. Exactly one student-data object is accepted, with optional surrounding JSON whitespace (space, tab, carriage return, line feed). A null root is rejected. JSON syntax whitespace is distinct from Unicode padding inside strings. After deserialization, model conversion checks students in file order, stopping at the first failure. No partial student list is published. On failure the file is preserved; help and exit remain available.

Each student requires valid name, studentId, and email values. Missing/null remark becomes empty text; missing/null labels and attendance become empty collections. Legacy tags and other unknown properties are ignored and are not saved again. Null student, label, or attendance entries are invalid.

The root object contains a persons array. For example, this is a valid minimal data file:

{
  "persons": [
    { "name": "Alex Tan", "studentId": "A0123456B", "email": "alex@example.com" }
  ]
}

Loading trims surrounding ASCII control whitespace, Unicode space separators, and the four supported Hangul fillers from text fields, labels, dates, and attendance groups before validation. Names also normalize these Unicode spaces and fillers to ASCII spaces and collapse repeated spaces. Internal remark, label, and attendance-group characters are preserved. Student IDs become uppercase; only email domains become lowercase. Limits apply after this normalization. Duplicate Student IDs, labels within a student, and attendance date/group pairs within a student are checked after normalization; label/group comparison ignores case but preserves internal spacing, Unicode spaces, and Hangul fillers. The normalized values are written on the next successful save.

Attendance is stored as attendance: a list of {"date": "2026-10-20", "group": "Tutorial 1"} entries per student. Dates must be real calendar dates in YYYY-MM-DD format; group names follow label constraints.

Successful startup reports N students loaded. (1 student loaded. for one student). A missing file reports No existing student data found. Starting with an empty student list. and allows normal use.

If main-window initialization fails, an error dialog titled Fatal error during initializing shows the exception details. Dismissing it exits the application with failure status; this is separate from student-data loading failure.
